# リアルタイム安全性

「リアルタイム安全」とは、同じ libsonare の DSP をライブの音声コールバック内でグリッチなく動かせる性質です。オンにする機能ではなく、音声経路が破ってはならない規則の集まりです。本ページはその規則と、libsonare がどう守るかを説明します。ストリーミング API は [リアルタイムとストリーミング](../../realtime-streaming.md) を参照してください。

## 音声コールバックには締め切りがある

音声は高優先度スレッド上でブロック単位で届き、各ブロックはスピーカーが必要とする*前*に、多くの場合は数ミリ秒以内に埋めなければなりません。一度でもその締め切りを逃すと、聞こえるクリック・ポップ・ドロップアウトになります。コールバックには厳しいリアルタイム締め切りがあるので、所要時間が無制限になり*得る*ものはコールバック内で禁じられます。

## コールバック内で禁じられること

| 禁止事項 | 音声を壊す理由 |
|----------|----------------|
| メモリ確保（`new`/`malloc`） | 予測できない時間ブロックし得る |
| ロック／ミューテックス | 他スレッド待ちで止まり得る |
| ファイル／ネットワーク I/O | レイテンシが無制限 |
| 無制限の処理全般 | 1 回の超過で締め切りを逃す |

規律は 1 つです。遅い作業（確保、ファイル読み込み、セットアップ）はコールバックの*外*で済ませ、コールバックは事前に作ったバッファを読んで処理するだけにします。

## libsonare が安全を保つ方法

libsonare のリアルタイム経路は、コールバックの規則を次の方法で守ります。

| 技法 | 意味 |
|------|------|
| 設定したブロックサイズ向けのバッファ事前確保 | 通常のブロックでセットアップ後のメモリ確保を避ける |
| ロックフリーなパラメータ更新 | UI からの変更で音声スレッドを止めない |
| パラメータスムージング | 値の変化でクリックを出さない |
| デノーマル対策 | 減衰時の極小浮動小数点値による CPU スパイクを避ける |

この 4 つで、同じ DSP コードがオフラインでもライブでも動きます。

## AudioWorklet

ブラウザではリアルタイム音声は **AudioWorklet** で動きます。メインスレッドとは別の、音声処理専用のコンテキストです。

想定する流れは次の通りです。

1. メインスレッドでオブジェクトを準備する。
2. 準備済みの処理を AudioWorklet へ渡す。
3. Worklet 内ではメモリ確保をせずにブロックを処理する。

このサイトはこの経路を `SharedArrayBuffer` なしで動かしているため、特別な COOP/COEP ヘッダは不要です。

::: details libsonare がリアルタイム安全性をどう実装するか
ミキサーのストリップ・バスと `RealtimeEngine` は、リアルタイム安全なコアを共有します。`StreamAnalyzer` も通常のサイズに収まるブロック向けに解析用バッファーを事前確保します。主な要素は次のとおりです。

- 事前確保バッファ（ブロックごとの再利用向けの `Mixer.createRealtimeBuffer()` を含む）
- ロックフリーなパラメータ変更
- デノーマル対策
- クリックなしの変化のためのパラメータスムーザー
- 並列経路をそろえるプラグインディレイ補償

`StreamAnalyzer` の `process()` は FFT、特徴量、進行中の音楽推定を同期的に計算します。通常の 128〜2,048 サンプル程度のブロックは構築時に予約した容量で処理できますが、大きなチャンクでは入力の非有限値除去、リサンプル、オーバーラップ用のスクラッチバッファーが拡張されることがあります。厳しいリアルタイムコールバックでは、コールバック外で構築・設定し、一定サイズのブロックを供給するストリーミングソースを使い、生成済みフレームの読み出しはコンシューマー側で行ってください。スレッドをまたぐ必要のある状態はロックフリーチャンネルで移し、直接読ませるのではなくテレメトリとして公開します。設定したブロックの処理が締め切り内に収まる限り、同じ DSP 実装をオフラインレンダリングとブラウザの AudioWorklet で使えます。
:::
